# 現行実装の致命的欠陥と根本原因分析 (`01_ARCHITECTURE_FLAWS.md`)

> **本書の目的**  
> 現行の初期実装に含まれる「設計の不備」「スケーラビリティの限界」を客観的に浮き彫りにし、なぜその実装のままでは開発が頓挫するのか、その根本原因を解明します。

---

## 1. 致命的欠陥一覧

現行の実装には、ゲームが大規模化・多機能化するにつれて確実に破綻する **5 つの致命的な設計欠陥** が存在します。

```text
[現行実装の 5 大欠陥]
1. 組み合わせ爆発: マテリアル ID に「状態（崩落）」を混入させたことによる ID 枠の浪費
2. ハードコード固定配列: MATERIALS: [MaterialDef; 7] による拡張性の完全な喪失
3. 密結合した判定ロジック: if mat == DIRT || mat == STONE などの名指し分岐
4. テクスチャデータのソースコード直埋め込み: メンテ不能な巨大マジックナンバー配列
5. 全画面無条件走査: チャンク分割とスリープ機構の欠如による CPU メモリ帯域の圧迫
```

---

## 2. 欠陥 1: 状態混入によるマテリアル ID の組み合わせ爆発

### 現行コードの問題箇所
```rust
pub const DIRT: u8 = 1;        // 土ブロック
pub const STONE: u8 = 2;       // 石ブロック
pub const LOOSE_DIRT: u8 = 5;  // 崩落した土粒子
pub const LOOSE_STONE: u8 = 6; // 崩落した石粒子
```

### なぜこれが破綻するのか？
「崩落（Loose）」という**一時的な物理状態**を表現するために、新しいマテリアル ID を消費しています。  
この方式を続けると、以下のような「状態」が追加されるたびに爆発的な数のマテリアルが必要になります：

* 燃えている土（`BURNING_DIRT`）、濡れた土（`WET_DIRT`）、凍った土（`FROZEN_DIRT`）
* 燃えている木（`BURNING_WOOD`）、濡れた木（`WET_WOOD`）、崩落した木（`LOOSE_WOOD`）
* 帯電した鉄、溶けた鉄、錆びた鉄……

$$マテリアル数 \times 状態数 = 膨大な ID$$

マテリアル ID は `u8`（最大 256 種）しかないため、わずか数種類の物質を追加しただけで **256 枠が完全に枯渇** します。  
さらに、土が崩落した際に「これは元々何の土だったのか？（元のテクスチャや物性）」の追跡が極めて困難になります。

### 正しい設計原則
* **マテリアル ID（`material`）** は、**「物質の固有の正体（土・石・水・木・鉄）」のみ** を表す。
* **状態（`flags` / `data`）** は、**直交したビットフラグ（崩落中、燃焼中、流動中）** で表す。
* 「土が崩落している状態」は、`Cell { material: DIRT, flags: FLAG_FALLING, .. }` で表現する。

## 3. 欠陥 2: 静的固定長配列による拡張性の喪失

### 現行コードの問題箇所
```rust
pub static MATERIALS: [MaterialDef; 7] = [ ... ];
```

### なぜこれが破綻するのか？
1. **型の硬直化**:  
   マテリアルを 1 つ追加するたびに `[MaterialDef; 7]` を `[MaterialDef; 8]` へ手動で書き換えなければコンパイルエラーになります。
2. **MOD / 外部設定の遮断**:  
   外部ファイル（`materials.toml`）からユーザーやゲームデザイナーがマテリアルを追加・調整することが原理的に不可能です。
3. **境界外アクセスのリスク**:  
   コードの別の場所で `id as usize` で直接インデックスした場合、配列長を超えると即座にクラッシュ（パニック）します。

### 正しい設計原則
* 最大 256 要素の固定容量レジストリ（`MaterialRegistry`）を定義し、起動時に TOML やスクリプトから動的に登録できるようにする。

## 4. 欠陥 3: 個別マテリアル名指しによる密結合分岐

### 現行コードの問題箇所
```rust
// world.rs 内
if cell.material == DIRT {
    // 土の処理
} else if cell.material == STONE {
    // 石の処理
}
```

### なぜこれが破綻するのか？
新しいマテリアル「砂利（GRAVEL）」「粘土（CLAY）」「氷（ICE）」を追加した際、`world.rs` 内のあらゆる `if` 文（当たり判定、崩落判定、流動判定）を探し出して書き換える必要があります。  
1 箇所でも書き忘れがあると、「粘土だけ水に流されない」「砂利だけ崩落しない」といった見つけにくいバグの温床になります。

### 正しい設計原則
* マテリアル判定は **物性フラグ（`MaterialFlags`）** で行う。
* `if mat.has_flag(CAN_COLLAPSE)` や `if mat.has_flag(WASHABLE)` と書くことで、シミュレーション側のコードを 1 行も修正せずに新マテリアルを何百個でも追加可能にする。

## 5. 欠陥 4: テクスチャデータのソースコード直埋め込み

### 現行コードの問題箇所
```rust
texture: [
    [120, 85, 45, 255], [130, 95, 50, 255], ... // 計 64 個の数値をベタ書き
]
```

### なぜこれが破綻するのか？
* ドット絵を描くグラフィッカーや開発者が、数千個の RGB 数値を手作業で打ち込むことは不可能です。
* 色を微調整したいだけの変更で、毎回 Rust の再コンパイルが必要になります。

### 正しい設計原則
* 画像ファイル（PNG 形式の 1 枚のテクスチャアトラス、例えば 128x128 ピクセルに 8x8 タイルが整列したもの）から起動時にピクセル配列を読み込む。

## 6. 欠陥 5: 全画面無条件走査（チャンクとスリープの欠如）

### 現行コードの問題箇所
```rust
for y in (0..self.height).rev() {
    for x in 0..self.width {
        self.update_cell(x, y, clock);
    }
}
```

### なぜこれが破綻するのか？
* 640×360 = **230,400 セル** を、毎秒 60 回、画面全体が完全に静止している時ですら無条件に走査しています。
* 1 秒間に **1,382 万回** のループが回り、CPU のメモリ帯域と電力を浪費します。
* 今後ワールドをスクロールさせたり、マップを 2000×2000 に拡張した瞬間にフレームレートが 5 FPS 以下に大暴落します。

### 正しい設計原則
* ワールドを **64×64 チャンク** に分割し、変化のあった領域（`dirty_rect`）のみを走査する。
* 静止した地中や海は完全に計算をスキップ（スリープ）させ、CPU 負荷を 90% 以上削減する。
