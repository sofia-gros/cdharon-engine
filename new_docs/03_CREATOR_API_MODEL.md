# Rustの公開APIをどう設計するか

## 設計の軸

Fabric APIから参考にする登録・イベント・フック・拡張の入口と、Phaserから参考にするScene・入力・リソースの統合を、Rustの型と所有権で実現します。継承や動的オブジェクトの形を移すのではなく、作者が何をしたいかからAPIを決めます。

構築はビルダー、実行中の操作はメソッド、共通の実装契約はトレイト、対象の保持は識別子とハンドルを基本にします。以下は採用する設計方針であり、API実装済みという記録ではありません。

## 生成時はビルダー、実行中はメソッド

```rust
let material = Material::builder("game:soil")
    .base(BasicMaterial::Solid)
    .block_size(16, 16)
    .texture(texture)
    .behavior(Powder::default())
    .build()?;
```

ビルダーは構築中の値を所有し、設定メソッドは原則として`self`を受け取って変更後の`Self`を返します。そのため一つの式で順に設定できます。`build(self)`はビルダーを消費して、検証済みの定義を返します。無効な値や組み合わせは`Result`で返します。

途中の値を変数に保持し、条件に応じて設定してから構築する書き方もできます。完成した値をレジストリへ登録する処理は、構築とは別の責務にします。

生成後の変更は、対象を取得して`set_velocity_x`などの操作メソッドを呼びます。生成と更新は扱う状態と検証時点が違うため、すべてをビルダーへ統一しません。

構造体は実装内部や設定データにも利用しますが、すべての設定について公開フィールドの一括指定と個別セッターの両方を重複提供することは要求しません。型付きの小さな値を引数にするなど、意味と使いやすさに応じて設計します。

## 基本定義と上書きの規則

基本マテリアルは、作者が再利用できる既定値と基本動作を提供します。作者の明示指定が基本定義より優先されるよう、基本定義と上書き項目を分けて保持し、構築時に解決する方針です。

`.base(...)`を後から呼んだだけで、作者がすでに指定したサイズや画像が消える設計にはしません。同じ設定メソッドを複数回呼んだ場合は後の明示指定を採用します。共存できない挙動など、暗黙に解決すべきでない競合は構築時に診断します。

## Sceneとシステムはトレイトで実装する

作者は自分の状態をRustの構造体へ保持し、エンジンが定めるトレイトを実装します。Sceneは読み込み・開始・更新・終了などの処理、独自システムは必要な実行処理と状態、プラグインは機能の登録と導入処理を定義します。

トレイトは「エンジンから呼び出せる処理の約束」です。Sceneの基底クラスを継承する仕組みを別に作る必要はありません。既定の処理はトレイトの既定メソッドや再利用できる部品として提供します。

作者が定義した素材の動作も、組み込み動作と同じ拡張契約へ接続します。独自動作を追加するたびに、エンジン内部の素材名の分岐や固定の列挙型を書き換える必要がないことを目指します。

## Contextを短く借り、対象はハンドルで保持する

エンジンはScene、世界、資産などを所有します。作者の処理へ渡すContextは、その呼び出し中に使う入口です。作者はContextや内部オブジェクトへの可変参照を保持せず、後の処理に必要な識別子を自分の構造体へ保存します。

| 保持するもの | 用途 |
| --- | --- |
| `TextureHandle`、`SoundHandle` | 検証済みの画像・音の参照 |
| `MaterialHandle` | 作者が保持する素材の参照。content確定後にWorld用IDへ解決 |
| `WorldId`、`EntityId` | 世界と、その中のオブジェクトを操作するための参照 |
| `ActionId` | 登録済みの入力アクション |

これらの型名は設計例です。キー文字列はファイルや登録の境界で使い、解決後は用途に対応する型を使います。音のハンドルを画像のAPIへ渡すなどの取り違えを防ぎ、破棄された対象への操作は診断します。

エンジンの管理下にある値へ一時的に`&mut`でアクセスするAPIを提供する場合も、その参照で何を変更でき、どの時点で変更が反映されるかを定義します。必要に応じて操作用のContextやコマンドを返す形を選び、内部配列の無制限な可変公開とは区別します。

## イベントとフックをRustで扱う

クリックなどのイベントには、対象とイベント型に対応したハンドラーを登録します。ハンドラーへはイベントの情報と、呼び出し時に利用できるContextを渡します。

コールバックが必要な対象は、所有する値や識別子として渡せるようにします。Scene自身を参照するクロージャをそのScene内へ長期間保存することを前提にせず、自己参照や複数の可変借用で作者が扱いに困る設計を避けます。

Scene経由で登録した購読はSceneの管理範囲に所属させ、終了時に解除します。購読の識別子を使った明示解除も提供する方針です。例の識別子は解除操作のための値であり、識別子を受け取らなかっただけで購読が即時終了する契約にはしません。

通知用のイベントと、標準処理の結果へ介入するフックを分けます。フックには型付きの引数と結果を用意し、実行順、取り消しや置換の意味、変更できる範囲を明示します。

## プラグインと共有定義

Cargoで拡張の実装をビルドへ含め、エンジンのビルダーからプラグインを登録する構成を基本にします。プラグインは必要な定義、サービス、システム、イベント、資産読み込みなどを登録します。

登録だけで完了する準備と、資産読み込み後に実行する準備を分けます。共有マテリアルの定義は準備完了後に検証し、世界から利用できるようにします。Sceneごとの資産と入力はSceneのライフサイクルへ所属させます。

共有レジストリへの二重登録、依存するサービスの不足、未知の参照などを診断します。拡張の状態をどこに保持し、どのように保存・復元するかも登録契約に含めます。動的ライブラリを実行中に読み込む方式を、この基本モデルから自動的に導入することはしません。

## 設計理由の根拠

Rustでは、メソッドが`self`、`&self`、`&mut self`を受け取ることで、値の受け渡しと変更を表現できます。構築と操作に応じて受け取り方を選ぶ設計とします。[Rustのメソッド](https://doc.rust-lang.org/book/ch05-03-method-syntax.html)

トレイトは、異なる型に共通の振る舞いを定義する仕組みです。Sceneや拡張に共通の呼び出し契約を設ける考え方に利用します。[Rustのトレイト](https://doc.rust-lang.org/book/ch10-02-traits.html)
