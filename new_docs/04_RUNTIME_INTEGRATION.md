# Sceneと各システムの管理・統合

## 統合の目的

エンジンは、Scene、リソース、入力、オブジェクト、世界、物理、音、独自システムを連携させます。作者はSceneや独自コードからAPIを呼び、エンジンが適切な処理先と実行時点へつなぎます。

この文書は統合の読み方を示します。内部の更新順は[07](07_ARCHITECTURE_AND_EXECUTION.md)、公開APIは[16](16_PUBLIC_API_CONTRACTS.md)、保存は[14](14_PERSISTENCE_AND_REPLAY.md)を基準とします。

## エンジン設定とゲーム定義の受け取り

実行基盤は、ビルドに含まれる機能、YAMLから読む実行設定、Rustコードから受け取る定義と実装を統合します。設定の詳細は[設定と拡張機能](05_ENGINE_CONFIGURATION.md)に従います。

起動時には、設定の形式と値だけでなく、要求された機能がビルドと実行環境で利用できるか確認します。検証済みの実行設定を保持し、Sceneやプラグインが必要な情報へアクセスできるようにします。

## プロジェクト、Scene、世界の役割

| 管理する単位 | 役割 |
| --- | --- |
| ゲーム全体 | 実行基盤、Scene管理、共通の資産や定義、作者が共有するサービスの管理 |
| Scene | ライフサイクル、表示するオブジェクト、入力の受け取り、Sceneに所属するイベントや処理の管理 |
| ゲーム世界 | 地形、マテリアル、セル、粒子、物体、世界に所属する独自状態とシミュレーションの管理 |
| 作者のモジュール | 登録する定義、独自処理、依存する機能、状態と後始末の管理 |

Sceneはゲーム世界へのアクセスを提供します。作者が必要に応じて同じ世界を保持しながらSceneを切り替えたり、UIを別Sceneとして重ねたりできる設計を目指します。Sceneを切り替えた場合の世界の保持・停止・破棄は、APIの方針として明示し、作者が制御できるようにします。

## Sceneのライフサイクル

Sceneの準備、資産の読み込み、開始、更新、停止・再開、終了を管理します。作者は構造体にSceneトレイトを実装し、エンジンが必要な時点でそのメソッドを呼びます。

SceneはCreated、Loading、Ready、Running、Paused、Stopped、Failedの状態を持ちます。load、必要資産の完了、start、update/renderの順で進みます。Pausedはscopeと表示を保持してupdateを止め、resumeでRunningへ戻します。Stoppedからの再startでは新しいscopeと開始処理を使います。

Sceneの終了時には、そのSceneに所属するオブジェクト、入力の登録、イベント購読、独自システムなどをどう停止・解放するか明示します。再開始時の登録と終了時の解除が対応する仕組みを提供します。

Sceneはエンジンに所有させ、各呼び出しで短期間だけContextを貸し出します。作者はContext自体や世界内部への可変参照をSceneへ保存せず、型付きの識別子を保持します。この設計で、更新処理とイベントの双方から必要な対象を操作できます。

イベント処理中にScene遷移などが要求された場合は、その場で呼び出し元を破棄せず、安全に処理できる境界で遷移を確定する方針です。作者のAPI呼び出しが要求の提出なのか、その場で完了する操作なのかを明示します。

## リソースの読み込みと利用

作者は画像、スプライトシート、関連データ、音などをキー付きで読み込みます。表示、マテリアル、アニメーション、音のAPIは、そのキーから準備された資産を利用します。

読み込みの進行、完了、失敗を取得できるようにし、準備が必要な資産を利用する前に状態を確認できるようにします。素材定義などに含まれる参照も、利用前に解決・検証します。

複数Sceneで同じ資産を利用する場合は共有できる管理を用意します。資産の共有範囲、所有、再利用、解放の条件を定義し、一つのSceneの終了が他の利用先を壊さないようにします。

コードでは画像や音のキーを読み込み境界で解決し、検証後は用途別の型付きハンドルを返します。所有者の保持とハンドルの有効性は別に定義し、ハンドルをコピーしたことだけで資産の保持期間が決まる設計にはしません。

## 入力とSceneの連携

キーボード、ゲームパッド、ポインター等の入力を、Sceneの入力APIから利用できるようにします。作者が複数の入力を共通のアクションへ割り当て、更新処理から状態を取得したり、イベントで応答したりできます。

クリック可能な表示オブジェクトと入力を連携させます。画面とゲーム世界の座標変換、カメラ、表示の重なりがある場合の入力先、UIが入力を受け取る条件を、統合されたAPIとして設計します。

メニューの操作とゲーム世界の操作が重なる場合、どのSceneやオブジェクトが入力を扱うかを作者が指定できるようにします。フォーカス、入力の有効・無効、押下状態とイベントの関係は正式な入力仕様で定めます。

Rust APIでは入力アクションを型付きの識別子として登録し、押した瞬間、押している間、離した瞬間を別のメソッドで取得します。機器の割り当てとゲームの移動処理を分け、同じ操作処理を複数の入力機器で使用できます。

## オブジェクトと2Dサンドボックスの連携

作者が追加した画像やキャラクターは、必要に応じて物理や世界との相互作用へ接続できます。画像、アニメーション、物理形状、位置、速度などを、同じ対象に対するAPIとして扱えるようにします。

マテリアル定義は、外観、セルや粒子の動作、衝突、相互作用へつながります。配置・破壊などの出来事から、定義された音と粒子を実行し、作者のイベント処理やフックも連携させます。

作者の更新処理、独自システム、物理更新、表示がどの順序と時間単位で動くかは明示します。エンジンが更新を管理し、作者が処理を組み込む時点と変更の反映時点を理解できるようにします。

## 独自状態と保存の連携

作者はゲーム、Scene、世界、個々のオブジェクトに必要な独自状態を持たせます。どの状態を保持し、どの状態を保存するかを指定する仕組みを提供します。

保存するデータと、実行時のハンドラーや資産への接続を区別します。復元時はStateCodecでデータと参照を復元し、登録済みの再接続処理からハンドラーと表示を作り直します。契約は[14](14_PERSISTENCE_AND_REPLAY.md)と[23](23_CONTENT_AND_STATE_SCHEMAS.md)に従います。

## 統合が成立したと判断する例

作者が公開APIだけを使って、次の流れを構築できることを確認します。

1. タイトルSceneが画像を読み込み、開始ボタンを表示する。
2. ボタンの入力イベントでゲームSceneへ遷移する。
3. ゲームSceneがマテリアル、画像、音、操作を準備し、世界とキャラクターを利用する。
4. キーボードまたはゲームパッドのアクションから、作者のコードがキャラクターを操作する。
5. 世界のマテリアルが定義された動作を行い、相互作用が音、粒子、作者の独自処理へつながる。
6. UIや別Sceneへ移っても、指定した世界と状態が保持され、入力とリソースの管理が整合する。
7. 保存・復元を利用する作品では、登録した独自状態と必要な処理を再開できる。

これを基本機能の利用と独自機能の拡張の両方で確認し、API提供と実行管理が一つのエンジンとしてつながっていることを検証します。
