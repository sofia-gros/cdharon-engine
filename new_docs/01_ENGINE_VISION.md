# エンジンの目的と制作モデル

## どのようなエンジンか

Charon Engineは、作者が独自の2Dサンドボックスゲームをコードで制作するためのOSSゲームエンジンです。Fabric APIのような機能の利用・拡張APIと、Phaserのようなシーン・入力・リソース管理を組み合わせます。これらを、世界、ブロック、マテリアル、セル、粒子、物理を扱う2Dサンドボックス機能と統合します。

作者はRustの構造体にSceneトレイトを実装し、読み込み、画面の生成、入力への応答、更新処理を記述します。生成時の設定をメソッドチェーンで組み立て、実行中は型付きのAPIでオブジェクトや世界を操作します。同じコードから、マテリアルや独自オブジェクトの登録、物理の操作、イベントへの応答、独自システムの追加も行えます。

Terrariaのようなブロックを使った建築・探索や、Noitaのような物質と粒子が相互作用する世界を制作できることを目指します。工場、パズル、戦闘のない作品なども、作者の規則で構築できることが必要です。

## 二つのモデルをどう組み合わせるか

| 軸 | 作者が得るもの | Charon Engineに必要な仕組み |
| --- | --- | --- |
| Fabric APIのようなAPI提供 | エンジンの機能へアクセスし、独自の内容や処理を追加・変更できる | 登録API、イベント、フック、基本定義、独自機能の組み込みと連携 |
| Phaserのような制作と統合 | Sceneから読み込み、表示、入力、音、更新をまとめて扱える | Scene管理、ライフサイクル、リソース管理、入力、オブジェクト生成、共通サービス |
| 2Dサンドボックス | 作ったゲーム世界で物質や物体を動かし、独自の相互作用を作れる | 世界管理、マテリアル、セルと粒子、衝突、物理、世界の操作、状態の保存 |

例えば、作者が登録したマテリアルをゲームSceneの世界に配置すると、その外観は読み込み済みの画像を利用し、動作はマテリアル定義と物理システムに従います。配置や破壊の出来事はイベントやフックから作者のコードへ届き、音、粒子、独自の処理につながります。

各機能が同じ識別子、オブジェクト、イベント、実行管理を通じて連携することが、エンジンの役割です。作者が個別の仕組みをすべて接続し直す負担を減らします。

## 作者が決めること

| 領域 | 作者が決める内容 |
| --- | --- |
| Scene | タイトル、本編、メニュー、UI、画面遷移、必要なSceneの構成 |
| リソースと表現 | 画像、透過PNG、スプライトシート、アニメーション、音、背景、カメラ、UI |
| 入力 | アクション名、キーボードやゲームパッド等の割り当て、操作の規則 |
| 世界 | 構成、生成、配置、施設、読み込みと更新の方針 |
| マテリアル | 名前、ブロックサイズ、画像、プロパティ、動作、粒子化、衝突、配置・破壊時の処理、相互作用 |
| ゲームオブジェクト | キャラクター、プレイヤー、アイテム、装備、道具などの構成と動作 |
| 独自システム | イベントへの応答、独自の挙動、ゲームの進行、保存する独自状態 |

作者が作るゲームコードが、機能の採用と組み合わせを決めます。エンジンは標準の動作とAPIを用意し、作者が必要に応じて利用、変更、置換、拡張できるようにします。

## エンジンが提供するもの

ゲームの起動と実行、Sceneの管理、リソースの読み込みと共有、入力、表示オブジェクト、カメラ、音、UI、イベントを統合して提供します。作者はSceneから一貫した方法でこれらへアクセスできます。

2Dサンドボックスのために、世界の管理、マテリアル定義、セルと粒子の動作、衝突、物体の操作、相互作用、保存・復元を提供します。これらの機能も作者向けAPIから利用・拡張できるようにします。

独自のクラスやシステムを登録し、エンジンの処理と連携させる入口を提供します。プロパティを保存するだけでなく、そのプロパティを使う動作と状態管理まで作者が実装できることが必要です。

## 基本マテリアルの役割

エンジンは、作者がそのまま利用したり、独自定義の出発点にしたりできる基本マテリアルを提供します。基本マテリアルを選び、必要な差分を記述して、定義を簡略化できます。

素材の性質、破壊や粒子化の可否、動作、配置・破壊時の演出、相互作用は作者が定義します。具体的な素材一覧や、作品固有の内容はこの段階で固定しません。

## 設定を配置する原則

YAMLの`conf.yml`は、エンジンをどう実行するかを指定します。ウィンドウ、描画方式と品質、音響、リソース管理、診断、共通の実行条件などを扱います。具体例の列挙ではなく、実行基盤に対する設定かどうかで配置を判断します。

何をゲームに登場させ、どう動作させるかはRustコードで定義します。ブロックサイズはマテリアルのビルダーへ、プレイヤーの構成や操作はオブジェクト作成とSceneの処理へ指定します。作者自身が別のゲームデータ形式を設ける場合も、公開APIへ接続できます。

新しい実装をビルドへ含めるにはCargoの依存やfeatureを使い、その実装をエンジンへ登録するにはRustのAPIを使います。組み込まれた機能の実行時の設定はYAMLから受け取れます。詳しくは[設定と拡張機能](05_ENGINE_CONFIGURATION.md)を参照してください。

作者が作成した透過PNGをブロックのテクスチャとして利用できるようにします。画像はローダーで登録し、マテリアルやゲームオブジェクトから同じキーで参照できるようにします。

物理セルは均一な基本単位、ブロックサイズは素材の配置footprint、画像のピクセルは表示資産の解像度、画面倍率はcamera/viewportの設定です。この関係と編集・衝突の仕様は[世界設計](09_WORLD_AND_STREAMING.md)に従います。

## 完成を判断する方向

作者がSceneとAPIを使い、自分の画像、入力、マテリアル、独自処理を持つゲームを構築できることを確認します。タイトルからゲームへの遷移、操作、世界との相互作用、必要な状態の保存・復元がつながることが必要です。

基本機能を使う作例と、独自の素材・動作・システムを追加する作例を用意します。建築・探索、物質シミュレーション、独自のゲーム規則を持つ異なる作品を、公開APIで制作できるか確認します。作例の内容がエンジン全体の必須規則にならないようにします。
